How the Attack Works

A mathematical breakdown of why nonce reuse in ECDSA completely breaks key secrecy.

ECDSA signature scheme

To sign a message with hash h, a signer picks a random nonce k, computes a curve point R = k·G, sets r = R.x mod n, then computes s = k⁻¹(h + r·d) mod n where d is the private key. The signature is the pair (r, s).

The critical assumption is that k is unique and unpredictable for every signature. If two signatures share k, r will be identical — a directly observable signal that the nonce was reused.

The math of key recovery

Given two signatures with the same nonce k: s₁ = k⁻¹(h₁ + r·d) mod n ← equation 1 s₂ = k⁻¹(h₂ + r·d) mod n ← equation 2 Subtract to eliminate d: s₁ − s₂ = k⁻¹(h₁ − h₂) mod n Rearrange for k: k = (h₁ − h₂) · (s₁ − s₂)⁻¹ mod n ← nonce recovered Substitute k back to solve for d: d = (s₁·k − h₁) · r⁻¹ mod n ← private key recovered

Attack flow

An attacker only needs two publicly visible signatures and the message hashes — all information available on a blockchain or in signed network traffic.

Observe (r, s₁) → Observe (r, s₂) → Same r detected → Solve for k → Solve for d

Real-world incidents

PlayStation 3 (2010) — Sony used a constant k for all firmware signatures. Fail0verflow published the master signing key, enabling piracy and homebrew. Fixed by switching to HMAC-DRBG.

Bitcoin wallet thefts — Multiple wallets using weak RNGs produced repeated r values on the blockchain. Researchers and attackers scanned the blockchain and drained funds from vulnerable addresses.

Android SecureRandom bug (2013) — Java's SecureRandom on Android was insufficiently seeded, producing repeated nonces in Bitcoin signing code. Google issued an emergency patch.

Mitigation Strategies

How to prevent nonce reuse in ECDSA — from best-practice library usage to architectural alternatives.

Best practice
RFC 6979 — Deterministic nonce generation
Derive k deterministically from the private key and message hash using HMAC-DRBG. The same inputs always produce the same k, but k is unique per (key, message) pair — making accidental reuse impossible by construction. Most modern crypto libraries implement this by default.
# Python — cryptography library (uses RFC 6979 by default) from cryptography.hazmat.primitives.asymmetric import ec from cryptography.hazmat.primitives import hashes key = ec.generate_private_key(ec.SECP256K1()) # k is deterministically derived — nonce reuse is impossible sig = key.sign(message, ec.ECDSA(hashes.SHA256()))
Recommended alternative
EdDSA / Ed25519 — nonce reuse attack surface eliminated
Ed25519 uses a hash-based deterministic nonce by design — the vulnerability class doesn't exist. Preferred for new protocols: SSH keys, TLS 1.3, Signal Protocol, WireGuard.
# Python — Ed25519 (deterministic, no nonce reuse possible) from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PrivateKey key = Ed25519PrivateKey.generate() sig = key.sign(message) # safe by design # Node.js const { generateKeyPairSync, sign } = require('crypto'); const { privateKey } = generateKeyPairSync('ed25519'); const sig = sign(null, message, privateKey);
Defense in depth
CSPRNG entropy validation
If you must generate k randomly, use OS-level entropy sources. Never seed with timestamps, PIDs, or predictable values. Validate entropy at startup.
# Python — always use secrets or os.urandom for key material import secrets k_bytes = secrets.token_bytes(32) # CSPRNG, not random.random() # Node.js const k = crypto.randomBytes(32); # not Math.random()
Detection
Signature audit — detect duplicate r values
Maintain a log of emitted signatures. Alert immediately on any repeated r value — it's an unambiguous sign of nonce reuse. On a blockchain, duplicate r values are publicly auditable.
# Simple duplicate-r detector seen_r = set() def check_signature(r, s): if r in seen_r: raise SecurityException("Duplicate r — nonce reuse detected!") seen_r.add(r)
